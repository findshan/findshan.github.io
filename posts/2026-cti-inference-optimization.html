把一个固定模型的推理从 238s 压到 30s:一次生成式推荐排序推理优化赛的工程复盘

2026 · findshan · 约 12 分钟

作者:findshan　·　赛事:百度商业 AI 技术创新大赛 —— 生成式推荐广告排序推理性能优化(百度 / 飞桨 AI Studio 主办)

一道"只许加速、不许改模型"的性能优化赛题。本文从官方 baseline(fp32 直跑 ~238s)讲起,按真实迭代顺序,记录我如何在严格合规约束下,用精度/算法重构 + 4 个手写 Triton kernel,把同一份模型的推理延迟做到 约 8×(238s → ~30s),且 AUC/PCOC 全程等价。

一、赛题:这是一道性能优化题,不是建模题

赛题是生成式推荐广告排序的推理性能优化:模型权重、组网结构全部固定,我要做的只有一件事——让它跑得更快,同时保证预测质量不下降。

评分公式:

score      = score_latency * 70 + score_model * 30
score_latency = max(0, (300 - latency) / 300)
score_model   = ((auc - 0.65) * 1000 + (0.15 - |pcoc - 1|)/0.15 * 10) / 360
               # 若 pcoc ∉ [0.85, 1.15] 或 auc ∉ [0.65, 1],score_model 记 0

两个关键含义:

  1. 延迟占 70 分,是绝对主战场。 模型分以 baseline 为上限——你没法靠"调得更准"加分,只能靠"别掉下来"保分。
  2. 质量是硬门槛。 PCOC 一旦跌出 [0.85, 1.15],模型分直接归零,几秒的提速换不回这 9 分。

合规红线(官方明确):

  • 不能改组网(裁层、删 expert 等视为违规,不计分);
  • 不能对序列采样或截断;
  • 量化等导致指标下降会扣分,超出范围记 0。

这几条几乎框死了所有"偷懒式提速"。能做的,只有在不改变数学输出的前提下,把同样的计算算得更快。

二、官方 baseline:模型长什么样

官方模型是一个序列推荐 CTR 模型,主体三段:

  • RepEncoder:28 个特征 slot,每个 slot 做 embedding 查表 + 按样本池化(sum pooling),拼成 [N, 28×512],再过 LayerNorm + Linear 投影到 d_model=512。
  • TransformerEncoder(8 层):每层 = 多头注意力(8 头)+ SMoE(8 个 expert,每 token 选 top-2)。注意力是块对角因果:一个 batch 把多个用户的行为序列拼成一条长度 N 的序列,每个用户内部做因果自注意力,用户之间互相屏蔽。
  • 最后一层 Linear 输出 logit。

一个 batch 里 N≈5000 个 token、约 20 个用户,用户长度极不均(最长能到 3000+)。这些数字后面很关键。

官方 baseline 的起点:fp32 原样直跑,平台实测延迟 ~238s。 这就是一切的零点。整条优化之路自然分成两段:第一段靠精度与算法重构,把 238s 砍到 ~68s(~3.5×);第二段靠手写 kernel,把 68s 再砍到 ~30s(~2.3×)。下面按这个顺序展开。

三、第一个、也是最重要的认知:平台到底怎么跑你的代码

动手前必须搞清楚评测机制,否则会白干。我通过逆向官方评测流程确认:

  • 平台的 evaluation.py 只 import load_model,然后直接驱动 model(batch);
  • main() 是死代码——你在 main() 里写的任何 autocast、compile、预处理,平台一行都不会执行;
  • 整个 forward 都被计时;
  • 数据通路里加 CPU 计算会严重反噬(我后来实测:在数据搬运里做一次 CPU gather,本地 5.7s 的活到平台变成 45s)。

这条认知推翻了一类常见做法:"把预处理挪到计时窗口外"在本地很好看,在平台一秒都省不到——因为平台没有"窗口外",forward 里的活该做还得做。唯一有效的方向是:让 forward 里总的计算/启动更少。

唯一的例外是 load_model()——它属于初始化,不计入推理延迟。这个细节后面救了我(编译/预热成本可以藏在这里)。

四、第一阶段:不写 kernel 的合规加速

4.1 精度与后端(fp16 + TF32 + flash SDPA)

把模型 model.half() 转 fp16,打开 TF32 与 flash/mem-efficient SDPA。fp16 只带来 ~0.0001 的 AUC 漂移(噪声级,PCOC 不变),换来可观的吞吐。仅这一步,就把 fp32 原样的 ~238s 拉到了 ~68s 量级(~3.5×)——精度选对是性价比最高的一刀。这一版同时作为后续 kernel 工作的受控基线:本地全量(2039 batch)forward = 68s。

之所以拿这版当基线,是因为后面所有版本都在同一台机器、同一份测试集、同样输入下测,数字才可比。机器本身的日内波动可达数倍,跨机/跨时间的比较没有意义。

4.2 一个算法层面的关键观察:被 mask 掉的 O(N²) 是纯浪费

原始注意力把整个 batch 的用户拼成长度 N 的序列,做一次 O(N²) 的注意力,再用一个 [N, N] 的块对角因果 mask 把跨用户部分清零。

但有个被忽视的物理事实:带自定义 mask 的 flash / mem-efficient SDPA 并不会跳过被 mask 的块——它照样把完整的 N² 算出来再 mask。实测每 batch N≈5000、20 个用户,dense 的计算量是"真实块对角"的 ~13×,绝大部分在白算。

修正方法:用户的 token 在 batch 里本来就是按用户连续排列的。于是逐用户切片、对每个用户单独跑 is_causal=True 的 SDPA——is_causal 让 flash kernel 跳过上三角、且完全不物化 mask。数学完全等价(逐位验证 AUC 不变),本地 68s → ~50s。

4.3 顺手的两个无风险小优化

  • baddbmm 融合 bias:MoE 的 bmm + bias 合成一次 torch.baddbmm,省掉作用在 [8, N, 1024] 这种 8 倍宽中间张量上的大 elementwise add。
  • 跳过 moe_loss:importance.std()/mean 是训练用的负载均衡辅助项,推理根本不用,直接不算。

两者数值等价,本地 50s → 47.5s。

这一阶段到此:68s → 47.5s,1.43×,全程 AUC/PCOC 等价,且一行 kernel 都没写。

五、第二阶段:先 profile,再决定写什么 kernel

继续往下,关键是不要凭直觉,要看 profile。这一步省下了大量在错误方向上的时间。

forward 的 CUDA 时间分布(实测):

算子占比是什么
MoE 的 bmm~41%8 个 expert 全算
flash attention~11%注意力
addmm~10%qkv / out / gate / 最后的线性层
segment_reduce + index_select~21%RepEncoder 的 28 次查表 + 28 次池化

MoE 是最大的肥肉:dense 实现把 8 个 expert 全算了,但每个 token 只用 top-2,4× 是纯浪费。这是头号目标。

5.1 一条重要纪律:很多"显然该快"的做法,实测都更慢

在动手写 kernel 前,我先试了几条"理应更快"的 PyTorch 级方案,结果全部反优化:

尝试预期实测原因
稀疏 MoE(sort + grouped GEMM)省 4× FLOPs50s → 63ssort/gather/scatter/同步的开销 > 省下的算力
torch.compile(max-autotune)kernel 融合本地快、平台反优化对隐藏测试集的新形状会在计时窗内重新 autotune
nested-tensor 注意力单次启动49s → 127sjagged 构造 + kernel 开销巨大
int8 / int4 量化低比特更快更慢 + 掉精度没有可用 int4 GEMM kernel;且量化掉点触发扣分
各种"预处理搬出窗口"省时间平台无效平台整个 forward 都计时

结论:这是一台"高效 GEMM 受限"的机器——dense 的 cuBLAS/cutlass kernel 已经很强,把它拆碎反而亏。 想赢,得写一个比"框架算子组合"开销更低的融合 kernel。这才轮到 Triton 出场。

5.2 Kernel 一:Triton fused MoE

稀疏 MoE 慢在哪?不在矩阵乘(grouped GEMM 本身没问题),而在外围的 sort / gather / scatter 物化大张量。

手写 Triton kernel 的思路:把 gather/scatter 直接融进 GEMM——

  • fc1 kernel:按排序后的 token 索引直接从原张量读(gather 融入 load),算完 relu 写出 h;
  • fc2 kernel:算完直接按 score 加权、用 atomic-add 散射回输出(scatter 融入 store)。

中间不再物化 xg、不再 index_add。单测对齐 dense:max abs err 9.8e-04(fp16 噪声级)。 全量:47.5s → 42s,AUC 等价。

对照实验很说明问题:同样是稀疏 MoE,手写 PyTorch 版 -25%,内置 grouped_mm 版 +6%,手写 Triton fused 版 +12%。瓶颈从来是 kernel 质量,不是思路。

5.3 Kernel 二:Triton RepEncoder 池化

RepEncoder 在平台上跑的是回退路径:28 次 embedding 查表 + 28 次 segment_reduce + 一次 cat,56 个小 kernel 外加一次大拷贝。

写一个 kernel:grid 是 (N, 28),每个 program 负责一个 (样本, slot) 的池化——按段 gather embedding 行、fp32 累加,直接写进 [N, 28×512] 的最终布局,省掉 cat/permute 的大拷贝。56 个 op → 1 个 kernel。

全量:42s → 36s,AUC 等价。

5.4 Kernel 三:Triton varlen flash attention(最大的一刀)

这一步前,我又 profile 了一次,发现一个反直觉的事实:

此时瓶颈已经不是 GPU,而是 CPU 调度。 总 CPU 时间 1.96s ≫ CUDA 1.02s。头号 CPU 消耗是注意力:逐用户的 SDPA 循环每 batch 要发起 160 次(20 用户 × 8 层)kernel 调用,光 CPU dispatch 就 754ms,而它的 GPU 计算只有 216ms。

也就是说,4.2 节那个"逐用户 is_causal SDPA"虽然算法对,但实现上被 Python 循环的启动开销拖住了。

解法是一个 varlen flash attention kernel(flash-attn-2 的在线 softmax + 因果掩码,用 cu_seqlens 描述每个用户的边界):所有用户一次 kernel 启动搞定,160 次 dispatch → 1 次。block→user 的映射每个 forward 只建一次,8 层复用。

单测对齐逐用户 SDPA(含 3160 长用户、单用户等极端情况):max err ~1e-3。 全量:36s → ~30s,AUC 等价。

六、最终结果

版本关键改动全量 forward相对官方 baseline
官方 baselinefp32 原样直跑~238s1.0×
第一阶段起点fp16 + TF32 + flash SDPA68s~3.5×
—逐用户 varlen 注意力50s~4.8×
—+ baddbmm 融合 + 跳过 moe_loss47.5s~5.0×
—+ Triton fused-MoE42s~5.7×
—+ Triton rep-pool36s~6.6×
最终+ Triton varlen flash-attn~30s~8×

注:238s 是平台对 fp32 原样的实测延迟,作为绝对零点;68s 起为同一台机器、同一份测试集下的受控对比,kernel 阶段的相对提升(68s→30s,~2.3×)在此口径下测得。

  • 两阶段、约 8× 加速:精度/算法重构(238s→68s)+ 4 个手写 Triton kernel(MoE fc1 / fc2、rep-pool、varlen flash-attn,68s→~30s),把固定模型的推理从 ~238s 干到 ~30s。
  • 全程 AUC / PCOC 等价(最大漂移 ~2e-4,纯 fp16 噪声),PCOC 始终在 [0.85, 1.15] 内。
  • 完全合规:组网、层数、权重一字未动,无任何序列截断/采样,无量化掉点。
  • 工程上做了完整护栏:三个 Triton 开关各自带数值自检 + dense 回退,任一 kernel 在目标环境不可用(如缺 triton)就各自退回原生实现,最坏情况退回纯 PyTorch 版本——保证正确性优先,加速其次。编译与预热全部放进不计时的 load_model()。

七、方法论:这次真正学到的东西

  1. 先搞清楚"代码是怎么被执行/计时的",再优化。 平台只计 forward、main() 是死代码——这个认知直接决定了哪些优化有效、哪些是自我安慰。
  2. 测量,不要假设。 "稀疏省 FLOPs""低比特更快""compile 一定快"这些直觉,在这台机器上几乎全错。每一条都用受控实验证伪/证实,才敢上。
  3. profile 要看对维度。 当瓶颈从 GPU 转到 CPU 调度时,继续优化 GPU kernel 是没用的;真正的解法是"把 160 次启动变成 1 次"。
  4. 框架算子打不过的地方,手写 kernel 能打。 但前提是瓶颈在调度/融合/无效计算,而不是在已经高度优化的 dense GEMM 上——后者别碰。
  5. 合规是设计约束,不是事后检查。 从第一行就守住"数学等价",反而逼出了更干净、更通用的优化(varlen 注意力、融合 kernel),而不是脆弱的取巧。

一句话:在"不许改模型"的牢笼里,把同样的数学算得更快,本身就是一门硬功夫。 从 ~238s 到 ~30s(约 8×),靠的不是某个 trick,而是"理解机制 → 量化定位 → 写 kernel 验证 → 守住正确性"这套闭环。
