从 1,368 到 1,148：真正卡住我的不是模型不够强

2026 · findshan · 约 15 分钟

2026 年 1 月，Anthropic 放出一道性能优化的题目。我用 Claude Opus 4.5 手动把它做到 1,368 cycles，离它自己那条 1,363 的参考线只差 5 个。2 月我停在这里。7 月我回来时换了模型，也换了工作方式——同一个问题从 147,734 重头跑，最后停在 1,148 cycles。

这不是一篇“AI 帮我写代码”的展示。我真正想弄清楚的是另一件事：当题目难到模型自己也答不出来的时候，卡住我的到底是它不够强，还是我的方式不对。

一、先说结果

Anthropic 把自己的 Performance Take-home 放出来时，题目看起来有点像一道普通的优化题：在一台模拟的 VLIW 机器上优化一个“树遍历 + 哈希”的 kernel，最后看它需要多少个 clock cycles。

但这台机器很快会让人失去耐心。它有 12 个标量 ALU slot、6 个向量 ALU slot、有限的 load/store 和唯一的 flow slot。我写出的不是“代码”，而是一长串必须在正确时间、正确资源上发射的指令。一个依赖关系没看清，程序不是慢一点，而是直接算错。

最初的 baseline 是 147,734 cycles。官方同时公布了一条参考线：Claude Opus 4.5 加上一版改进过的 harness，能做到 1,363 cycles。中间隔着一堵看起来不像人类翻得过去的墙。

我最后停在 1,148 cycles，大约是 baseline 的 129 分之一，比那条参考线低了 215 个 cycles。但这不是我最想讲的部分。我更想讲的是：同样是这道题，我在 1 月和 7 月做的事几乎完全不同，而结果也完全不同。

二、三个阶段、两个模型、两种分工

在往下讲之前，我想先把“谁在干活”说清楚，因为它比数字更能说明问题。

这道题的知识不在任何公开语料里——这台机器的 ISA、每条指令的 load latency、slot 之间的竞争关系，全都得现场从 simulator 里一行行读出来。模型查不到，只能我告诉它。这一点决定了三个阶段的分工是彻底不同的：

我做什么模型做什么结果
第一幕
2026 年 1 月
Claude Opus 4.5		读 simulator、判断 load latency、检查寄存器的读写集合、决定下一条路走哪把我的判断变成 scheduler 和 vector kernel，然后一轮轮跑实验2,032
第二幕
2026 年 2 月
Claude Opus 4.5		还是在做上面那些事，但越来越多的时间花在重复提醒它“这条已经失败过”同上1,368
第三幕
2026 年 7 月
Claude Opus 4.8		退到旁边，一次性把规则和边界定好，写 harness，事后审计日志在边界内自己选下一个实验、自己判断保留还是丢弃1,148

一句话总结：前两幕，我是那个“记得住的人”，模型是那双“写得快的手”；第三幕我把“记得住”这件事交给了文件，它才开始自己往前走。

三、第一幕（1 月，Opus 4.5）：我把判断说给它，它把判断写成代码

Anthropic 刚把题目放出来，我就开始做了。不是把题目扔给模型然后等答案，而是很像结对编程：我读 simulator、讨论 load latency、检查寄存器的读写集合；它负责把这些判断变成 scheduler、vector kernel 和一轮又一轮的实验。

最早的改动很朴素：把标量操作变成 SIMD，把三个可以融合的 hash 阶段改成一个 multiply_add。第一天结束时是 2,032 cycles——从 147,734 出发，一天之内跨过了两个数量级。月底继续推到 1,689。

每一次下降都很令人兴奋，也每一次都很容易让人误判。某个 mux 在纸面上能省掉大量 load，真正运行却会撞上 flow slot；某个看起来无害的寄存器复用，会在几轮之后变成 WAR hazard。我花了很多时间学一件不那么浪漫的事：在这种机器上，“更聪明的代码”不等于“更快的代码”。

公开的 anthropic_performance_solution 保存的就是这条路线。

四、第二幕（2 月，还是 Opus 4.5）：差 5 个 cycles

2 月我继续用同一个模型往下推：cross-vector 的 wave scheduler 把数字带过 1,425，然后是 1,415、1,388，最后停在 1,368。

1,368 和官方那条 1,363 之间，只差 5 个 cycles。我当时在 CHANGELOG 里写下的是：the bottleneck remains the final speed threshold (expects <1363)。2 月 14 日我又记了一笔——目标是压到 1,300 以下，那天做了三个实验，全部失败。

但真正的问题不是“还差 5 个 cycles”。是到了这个阶段，模型已经不知道哪条路试过了。

我得一遍遍把“这个寄存器不能再动”“这条上次炸了 scratch”“这个版本为什么留着”重新讲给它听。对话越拉越长，上下文越来越挤，到最后，我成了它唯一的内存。

所以那时候卡住我的，其实不是它不够聪明，而是它记不住。

2 月我停在了 1,368。但我心里一直挂着同一个问题：这个瓶颈，到底是模型不够强，还是我做实验的方式不对？我想继续探索下去。

五、我换的不是模型，是我坐的位置

7 月我回来接着做。第一件事确实是换模型——Opus 4.5 已经下架了，我把新一代的 Claude Opus 4.8 接进来。我当时想看的是最直接的那件事：光是模型变强，能不能直接把 1,363 撞过去。

不能。

于是我决定改的不是模型，是我坐的位置。因为我想明白了一件事：真正的瓶颈从来不是“模型还不知道某个技巧”，而是整个实验过程都挂在一段对话的上下文里——哪条路失败过、哪个寄存器不能碰、上一轮为什么保留了这个版本，全靠人记着。如果这些信息只存在于我的脑子里，那所谓的“自主优化”就只是换了一个说法。

所以我先写了一个小框架，只有几条硬规则：

  1. agent 只能修改 kernel；
  2. 每次只做一个实验；
  3. 所有结果都通过冻结测试验证；
  4. 变好就保留，变差就丢弃；
  5. 实验历史写进文件，下一轮从历史继续。

这个框架后来叫 perf-evolve。

program.md
     │
     ▼
agent → lab/perf_takehome.py → experiment.py → frozen tests
                                      │
                                      ├─ experiments.jsonl
                                      ├─ best.py
                                      └─ progress.png

program.md 告诉 agent 如何思考；experiment.py 负责测量和记录；analyze.py 告诉它当前究竟是 load、VALU 还是 scratch 在限制进步；best.py 保存当前最优解；experiments.jsonl 则像一份不会忘记失败的实验日志。

这里最重要的不是自动化，而是边界。让 agent 自由修改所有东西，很快就会得到一个“通过了自己改过的测试”的漂亮数字。真正可信的进步，必须来自一个 agent 不能随意改动的评分系统。

六、第三幕（7 月，Opus 4.8）：同一个问题，我从零重跑了一遍

放进 harness 之后，我做了一个决定：不从 1,368 接着往下推，而是从 147,734 重头开始。

理由很简单——我想知道这条流程本身行不行，而不是想抢救那个数字。

真实的过程并不漂亮。7 月 2 日晚上第一条实验记录还是原始的 147,734；六分钟后到 2,254；不到一小时，到了 1,581——这已经超过我 2 月手动一整个月的 1,368。第二天早上，对角 wavefront 发射把它带过了 1,300。7 月 6 日，停在了 1,148 cycles，大约 129 倍。整个过程留下了 209 条可复查的实验日志。

但我想老实说，中间并不是一路顺风。最难受的时候，我在对话里写下的原话是：

“花了多久，怎么用这么强的模型都没有打败官网的，这个自进化的 harness 好像打不败官方的嘛。”

后来我想清楚了，只留下一句：

“继续破，毕竟我们使用了最强的模型，我们想要看看它的下界是多少。”

这两句话可能比 1,148 更能说明我在做的事——不是为了赢过一个数字，而是想知道它到底还能走到哪。

七、模型变强了多少，我没法把它单独摘出来

这里我必须诚实：我没法把 1,148 单独归功于模型，也没法单独归功于流程。 因为等 7 月我回来的时候，Opus 4.5 已经下架了——我没法用同一个模型再跑一遍 harness，把“换模型”和“换流程”这两件事干净地分开。这是个遗憾。如果当时能做这个对照实验，这件事会讲得清楚得多。

但有一件事我可以确定：2 月卡住我的原因，从来不是模型不够聪明，而是它记不住。而这条流程第一次跑起来，不到一小时就超过了我手动一个月的成果。

所以我对“模型能力”的判断也变了。以前我以为，模型变强的意义是它一次能想出更好的 kernel。现在我更相信：它变强的意义，是能撑住更多轮失败的实验而不跑偏。 模型能力是上限，工作方式是我能多快接近上限的速度——很长一段时间里，我只有前者。

八、这条线还没走完

我当然试过继续往下压。但这次机器开始明确告诉我边界在哪里。

每个元素每轮至少要完成 XOR、12 个左右的 hash 操作和分支更新；总算术量已经接近 VALU/ALU 的吞吐上限（val^node + hash + branch 大约 16 个操作，乘以 4096 个元素再乘以轮次，除以每 cycle 60 个操作）。单看算术，下界大约在 1,138 cycles——1,148 只比它高 10。另一方面，深层 tree gather 没有真正的向量 gather 指令，load latency 也不会凭空消失，那里还压着一个大约 1,300 的下限。

也就是说，后面几乎没有低垂的果实了。这给整件事提出了一个比“继续跑实验”更难的问题：什么时候应该停止。 如果一条流程只会奖励更小的数字，它会不断尝试一些看起来聪明、实际上只是在消耗时间甚至破坏正确性的方向。下一步要让它理解的不只是 better，还包括 why better、how trustworthy，以及还有没有空间。

这段经历最后留给我三件事：

  1. 记住失败，比记住成功更重要。 失败过的路径如果没有留下来，下一轮就会重新踩进去。
  2. 正确性必须先于性能。 一个靠改测试换来的 1,200 cycles 没有意义；一个能站住的数字才有意义。
  3. 模型能力和工作流能力不是一回事。 在我还不懂的知识上，模型的价值是把我的判断变成能跑的代码；在反复试错的阶段，它的价值是能不厌其烦地试下去——只要它记得住。

结语：1,148 会过时，那条路不会

1 月我以为故事是“我把一个困难题做到了 2,032”。2 月我以为故事是“我只差官方 5 个 cycles”。现在我觉得，那两段都还不是最重要的部分。

更重要的是我看到了一个很小的转折：当我把约束、测量和记忆都搭好之后，模型不必每次都从一句“请帮我优化”重新开始。它可以带着昨天的失败，走向今天的实验，再把今天的结果留给明天。

这离真正的 autonomous research 还很远。它仍然需要更好的停止条件、更可靠的 provenance、更公平的模型对照，也需要我诚实记录哪些地方仍然依赖人。但至少在这个很小、很具体的 VLIW 世界里，我看见了一个值得继续追问的可能性：

也许 AI 研究的下一步，不只是让模型给出更好的答案，而是让它拥有一条不会轻易中断的、可以继续做实验的路。
